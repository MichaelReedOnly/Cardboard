# Drag and Drop into Columns — Implementation Plan

**Goal:** In Manual sort, move an unpinned card to the end of any visible column, including an empty one. Preserve every other card’s column and relative order, keep pinned cards in place, and persist the result across reloads.

**Current behavior:** `src/app.js` assigns each visible card to the shortest estimated column on every render. A card drop calls `moveCard` in `src/model.js` to change flat order. The next render can reshuffle unrelated cards and has no way to target an empty column.

**Confirmed responsive behavior:** Use the existing 1–5 column breakpoints. A narrower view initially projects the wider layout into the available columns. Save explicit moves separately for each column count. Restore that count’s saved arrangement when the window returns to it.

| Step | Implementation | Requirement addressed |
| --- | --- | --- |
| 1. Add a saved Manual layout | Store ordered card IDs per column, board, and column count. Validate references and uniqueness. Older saves and JSON imports without layouts still load; use the existing height-based arrangement to initialize the first layout. Keep persistence behind `src/storage.js`. | A column is a real destination. Moves survive reload and backup/restore. |
| 2. Define and test the move | Add `moveCardToColumnEnd(state, boardId, columnCount, cardId, destinationColumn)` in `src/model.js`. Check the card belongs to the board, is unpinned, and the destination exists. Remove the ID from its original column and append it to the destination. Leave other IDs in place. A card already last in its target column is a no-op. | The moved card lands last, other cards keep their positions in the layout, and pinned cards stay put. |
| 3. Render saved columns | In Manual sort, render from the saved full-board layout, then apply search and filters. Reconcile placement when cards are added, deleted, pinned, or unpinned. Keep Title and Date views independent of the Manual layout. Preserve existing eligible card-to-card reorder and keyboard move controls by routing them through the saved layout too. | Filtering, sorting, and editing won’t erase a manual placement or move unrelated cards. |
| 4. Add a drop target per column | Render a labeled bottom target even in empty columns. Highlight valid destinations during a drag. Only show drop behavior for eligible cards in Manual sort. Use the same move operation for a keyboard-accessible “Move to column” control. Save through the repository before displaying success; if saving fails, keep the prior layout and show the error. | Every visible column can receive an unpinned card, with a clear and reliable result. |
| 5. Handle viewport changes | On crossing a breakpoint, show the layout for the new column count. If none exists, derive one for display from an existing wider layout, folding overflow into visible columns without losing cards; save it only after an explicit move or layout edit. Restore saved arrangements when returning to their column count. | Fewer columns remain usable, and a resize does not undo saved desktop placement. |
| 6. Verify and close | Add model tests for populated and empty destinations, same-column moves, no-ops, pinned protection, and unchanged neighbors. Add storage tests for older saves, layout round-trip, invalid imports, and failed writes. In the browser, test drag, keyboard move, reload, filtered views, and narrow/wide resize. Record the results on the requirement card before marking it Done. | Each acceptance check has direct evidence. |

**Example:** Before: column 1 `[Pinned, A, B]`, column 2 `[C]`, column 3 `[]`. Drop `A` at the bottom of column 3. After: column 1 `[Pinned, B]`, column 2 `[C]`, column 3 `[A]`. Reload and confirm the same layout.
